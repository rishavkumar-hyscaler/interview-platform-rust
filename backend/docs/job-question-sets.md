# Job question sets

Creating a job now queues three unique sets before any candidate is invited. The default preparation duration is 30 minutes; the interviewer can choose 5–180 minutes when creating the job. Each set uses the same validated blueprint/draft/reference/critique/embedding-deduplication pipeline previously used by sessions. Six questions are generated by default (the existing provider configuration still controls the count).

The interviewer can open **Jobs & invitations → Question sets** to see queued/running/ready/failed sets, inspect unused questions and their worked reference answers, refresh status, or retry failed sets. The panel polls while work is pending. References and rubrics are never returned through candidate APIs.

Invitations reserve a completed, unused set with the same duration in the invitation transaction. Question rows are attached to that session; the set is never assigned again, even if its candidate never starts. Consuming a set queues a replacement so the pool has three unused ready/pending/running/failed slots. Failed slots stop after three attempts (or immediately on a fatal provider error) and require an explicit retry; they do not silently generate unlimited paid requests.

When all sets are busy or the invitation uses another duration, the existing per-session generation path remains available. Candidate work takes priority over stock replenishment. For unused stock, fresh attempts run before retries and newer jobs run before the historical backlog, across interviewer accounts. Completed sets can be assigned even when AI is temporarily unconfigured. Unfinished sets require a configured provider and the running generation worker.

## Storage and API

One additive migration, `202611050002_job_question_sets.sql`, adds `question_sets` and the job's preparation duration. Questions, worked answers, rubrics and vectors remain in `interview_questions`; unassigned questions have a set ID and no session ID. Existing session questions and answers are preserved. Existing jobs receive three queued sets, without fabricating users or interview sessions. Applied migration files are not rewritten.

- `POST /api/v1/jobs`: optional `preparation_duration_minutes` (default 30), plus the existing job fields. Queuing is atomic and idempotent with job creation.
- `GET /api/v1/jobs/{job}/question-sets`: owner-only status and unused question/reference previews. Returns up to 60 recent set records and 120 unused questions.
- `POST /api/v1/jobs/{job}/question-sets`: owner-only retry of failed unused slots and top-up of missing default-duration slots; requires configured AI.
- Existing invitation and session-generation endpoints retain their contracts.

Leases, bounded retries, row locks, per-job publication locks, unique prompt fingerprints and semantic comparisons cover both pool and session generation. Job-bank deduplication includes unused and previously assigned sets. Row-level security isolates the new table as well as questions; candidate access remains session-scoped. Request/task logs do not contain prompts, references, tokens or provider keys.

Run `cargo run -- --migrate`, then restart the backend to activate the new worker. The frontend shows status after refresh. The new database regression covers pre-generation, three distinct sets, idempotent creation, lease recovery, simultaneous assignment, replenishment, offline assignment, candidate/reference privacy, empty-pool fallback, fatal errors and explicit retries. It uses a local mock provider; it does not establish live-provider question quality.

Generation v3 validates/deduplicates/reviews prompt-only drafts before requesting any reference answers. References are prepared and reviewed per question with bounded concurrency and one local repair; deterministic quality failures stop rather than repeating the full set through worker retries. Detailed reviewer findings go internally to the repair request; public status retains a short diagnostic. The quality gate remains mandatory. See [staged generation and time limits](generation-timing.md).
